# P5 native settings design

Authority: approved mobile requirements/design and execution plan. This refines the native settings work; it does not authorize production administration. Source basis: read-only archived web main3669e60864a38df4738de20fafe7b72675a230a0. Refresh each operation against current reviewed core before implementation. Current editor slice has priority. Astra reviewed and approved this design after corrections for actual server behavior. Implementation and runtime acceptance remain pending.

## User task and native structure
The user wants board and system settings to feel intentional, connected to their content, and native. Retain approved web taxonomy: Displays → selected display → Overview, Settings, Playback; Settings → General, Account, Network, AI, System, Advanced. Use standard SwiftUI List/Form/detail navigation, restrained section footers and normal separators. Avoid nested cards, repeated explanatory banners, mode-card decoration copied from web, or forcing every group onto one long form. Selected display name remains in destination context; board controls never mutate an implicit primary target.

Display Settings owns identity/name, output connection, geometry and presentation. Playback owns schedule/default page, silence, transition and cadence. System Settings owns installation-wide identity/time/date/location, output routing, integration/update policy, network, account/devices, maintenance and advanced controls. Label app-only connection, remembered sign-in, local draft recovery and app appearance separately as “This app”; server changes must not silently alter local preferences. Standard sidebar/detail on tablet, push navigation on compact. State lives outside transient views so resizing does not reset edits.

## First implementation package
Implement native General and selected-display connection/settings with actual read/edit/save/readback; reuse a bounded schema form for installed output settings and later integrations. Scope is deliberately one useful native path before all administrative panels. The existing server-administration placeholder will be replaced incrementally, without marking hidden/pending workflows complete. Use synthetic/isolated server writes only. Later Account/Network/AI/System/Advanced workflows remain required and tracked; no production authority is needed to implement/test them against fixtures.

General fields: instance name, timezone, time/date formats from /config/general; location coordinates and solar-time lookup from /settings/location; installation output routing from /settings/output; /v1/install schedule/default-page fallback remains visibly distinct from per-board settings. Show the server's current values and choices, never silently apply device timezone or default enums.

Selected-display name, paused, schedule_enabled, auto_restore and default_page_id use sparse PATCH /v1/boards/{concreteID} where supported. Broader geometry/output connection uses the exact settings-v4 output_config representation. /settings/board currently replaces the full boards array; retain the original lossless list, stable IDs and masked credentials in client requests, but do not claim end-to-end preservation of unknown top-level board keys: inspected SettingsService.set_boards normalizes every entry through BoardInstance.from_dict(...).to_dict() and can discard them. Detect unverified top-level board fields across the entire list and block replacement until an audited server contract preserves them or the data is explicitly reconciled. This also applies to name/auto_restore PATCH, which invokes set_boards internally. Typed known fields and verified nested output_config extensions need separate preservation fixtures. Do not accidentally submit flat api_mode/host/port/keys alongside output_config; web toV4Write removes these compatibility fields. Only one of devices/boards/board_type is acted on per request, in that priority; native sends exactly one. Geometry changes show returned retargeted_pages and incompatible_references. A successful configuration save is not a successful device connection or observed output.

## Data and save behavior
Use existing LosslessJSON for full replacement documents and typed projections for supported controls. No Double round trip for opaque extension numbers. Allowlisted sparse fields for small resources; original snapshot and verified connection scope plus request/session epoch for every edit. Each screen has explicit dirty/valid/pending/saved/conflict/uncertain state. Save is an intentional action on a cohesive settings form; no autosave-on-blur for secrets or geometry. Saved refers only to acknowledged submitted snapshot; edits made while awaiting response remain dirty. Uncertain write must be read back explicitly, never automatically repeated. Inspected PATCH /v1/boards applies pause/schedule before validating a default-page reference and can fail later while renaming: dispatched400/404/503 cannot be assumed side-effect-free. Enter a readback-required state on such failures, show per-field current/attempted values after reconciliation, and never claim an atomic combined Save. General spans separate resources, so use per-resource Save/outcome instead of pretending one transaction. Existing controls need the same partial-write regression during P5 refresh. Cancel/leave offers discard or continued editing; secrets are not placed in ordinary draft exports/logs/screenshots.

Unlike pages/collections/schedules, inspected settings endpoints expose no revision token. Do not invent expected_revision or claim atomic conflict protection. For full-board replacement, re-read before Save and compare to the captured baseline; if changed, require explicit reload/review before constructing another replacement. This reduces stale overwrite but does not close the server's read/write race. Record this limitation and prefer sparse v1 edits wherever available. Masked baseline rereads cannot detect a credential rotation when both responses return***; never claim secret conflict detection from masked comparison. A server revision capability would be needed to guarantee atomic board-settings conflict rejection. Missing target or changed connection invalidates Save and preserves safe nonsecret edits for review, never retargets primary automatically.

## Bounded schema form
Support the actual core JSON schema subset: strings, numeric lexemes, booleans, enum labels, arrays and nested objects, required/min/max and bounds; root ui:sections; sibling and board-fact ui:visible_when grammar. Use native Picker/Toggle/TextField/SecureField/DisclosureGroup and list navigation. Unknown widget/schema nodes are preserved and labeled unavailable, not dropped or silently edited as arbitrary JSON. Retained defaults are display fallbacks, not inserted into outgoing values merely by rendering.

Reuse core visibility test vectors: exact JSON equality (true !=1, string1 !=number1), omitted uses schema default, explicit null remains null, @device_type/@device_model reads board facts; malformed conditions remain visible. Settings' true conditional invisibility differs from collapsing a section: core skips validation for conditionally hidden fields but retains their values. Collapsed visible required/invalid fields still block Save and expose an error route. Canvas validation semantics must not be copied indiscriminately into this settings grammar.

Secrets distinguish unchanged masked value, replacement and intentional clearing. Existing *** sentinel is echoed only for the same stored board and path under source-defined matching; new board credentials cannot reuse ***. Missing output schema can mask the entire output_config as ***; preserve it without pretending to render/edit it. Native input must not treat *** as a literal password. Arrays with per-tile secrets need exact source matching rules before reordering; preserve unsupported cases read-only until validated. Existing output actions are explicit user actions with target/config/generation binding and independent result states; saving does not run identify/test/discover implicitly.

## Account/session and unsupported actions
Existing Transport.APIRequest.browserSession supports Origin and CSRF context, but capability and browser-session applicability still require evidence. src/auth/browser_routes.py rejects Authorization token even alongside valid cookie, requires a qualifying stored session, permitted origin and per-session CSRF. resolve_browser_session accepts kind browser OR legacy for v2 cookies; the native password-login cookie can qualify without changing user agent. Probe the actual context endpoint under the current cookie rather than assuming native clients are excluded. Fetch /auth/sessions/context immediately before each applicable mutation, bind to same session/connection epoch, no stale nonce after logout/account changes. Do not convert a native/MCP token to admin authority or invent an origin to bypass server refusal. If unavailable, explain the exact requirement with safe deployment-relative web route. Keep the native workflow implemented/tested for supported sessions; source refusal is not a license to omit all administration.

## Acceptance and evidence
1. General and display settings read, edit, save and reopen on phone/tablet; title always identifies server or board. Sparse requests omit untouched fields and null differs from omission.
2. Client full-board replacement preserves large integers, other boards and exact secret placeholders; audited fixtures prove server preservation for supported fields, while unknown top-level board fields block normalizing operations rather than silently losing data; reordered/deleted/new tile secrets cannot move credentials by index accidentally. Source fixtures exercise output-config whole-mask case.
3. Invalid numeric intermediate strings remain editable; visible collapsed invalid fields have a repair route; conditionally hidden settings follow server visibility grammar. Save disabled with clear reason.
4. Scope/session/target switches while loading/saving cannot adopt late responses. Missing selected board never becomes primary. Dispatched board PATCH failure, including400/404, requires readback for possible partial application. Timeout is uncertain, 412 is not retried where supported; unsupported revisions are not invented.
5. Save/readback result, restart-required, geometry retarget warning, test/identify outcome and physical observation remain distinct. No live actions during this package.
6. Native compact/tablet journeys, large text, dark mode, keyboard reachability and accessible labels/actions. Actual screenshots show completed forms and readback, no placeholder or empty diagram counted as parity.
